Product + Engineering + Publication Blueprint

Turn the existing Kubernetes dashboard into a real open-source troubleshooting tool

The current implementation is already a functioning Kubernetes operations dashboard. The main transformation is not a frontend rewrite: it is replacing the local shell/Python/proxy runtime with a single Go binary, generalizing application-specific assumptions, and strengthening the relationship-aware troubleshooting and capacity-diagnosis story.

01 — Foundation

Executive Summary

The product should become a local, browser-based Kubernetes troubleshooting application installed as a single binary.

Core recommendation: Preserve the current UI and workflow. Replace the helper processes underneath it with one Go process that serves the UI and talks directly to Kubernetes using client-go.
brew install <owner>/tap/<tool> │ ▼ <tool> │ ┌─────────┴──────────┐ │ │ Embedded Web UI Go Backend │ │ └──── localhost ─────┤ │ client-go │ ~/.kube/config │ ▼ Kubernetes API
02 — Foundation

Current State

The current dashboard is already a real operational tool, but its runtime is split across multiple local processes.

HTML Dashboard

Nodes, workloads, troubleshooting, resource usage, logs, events, describe-style summaries, workload navigation and destructive actions.

kubectl proxy

Serves the static HTML and proxies browser requests to the Kubernetes API.

Python Log Helper

Uses kubectl exec to tail files written inside containers that are not available through normal stdout logs.

start.sh │ ├── kubectl proxy :8001 │ ├── serves dashboard HTML │ └── proxies Kubernetes REST API │ └── Python helper :8002 └── kubectl exec → tail files inside containers
Why this still feels like a utility: the user must have multiple runtimes and processes present, ports are exposed separately, the HTML directly understands Kubernetes API paths, and the application contains environment-specific assumptions.
03 — Foundation

Product Thesis

The differentiation should not be “another Kubernetes dashboard.” It should be troubleshooting through relationships and operational context.

Proposed product promise

Understand what is happening in a Kubernetes cluster by moving naturally between workload, pod, node, runtime usage, events and logs without reconstructing the topology manually.

This is a stronger identity than a generic resource browser because the tool explains how Kubernetes objects relate and how those relationships contribute to failures or wasted capacity.

04 — Product

Target Product Architecture

One local executable, one local HTTP server, one Kubernetes client, one embedded frontend.

Runs locally and uses the operator's existing credentials.

No Python

File-log retrieval and exec move into the Go backend.

05 — Product

Nodes

The Nodes view should remain one of the strongest differentiators because it combines scheduling reservations with actual runtime usage.

Cluster-wide node view

  • Ready / NotReady status
  • Node age and instance type
  • CPU requests vs limits vs allocatable
  • Memory requests vs limits vs allocatable
  • Pod count and pod capacity
  • Metrics availability detection

Per-node diagnostic view

  • Pods running on the selected node
  • Per-pod CPU and memory requests
  • Actual CPU and memory usage
  • Reserved-but-idle capacity
  • QoS class and restart counts
  • Sort by usage, request or waste
Research-worthy angle: requested resources influence scheduling even when they are not actually consumed. Making the difference between “reserved” and “used” immediately visible can expose stranded cluster capacity.
Node allocatable CPU: 8.0 cores Requested by pods: 6.4 cores Actually used: 2.1 cores ───────── Reserved but idle: 4.3 cores
06 — Product

Workloads

Workloads should be a relationship browser, not just a collection of Kubernetes tables.

Deployments

Replicas, availability, update state, owner relationships and pod drill-down.

ReplicaSets

Intermediate ownership layer used to connect Deployment → Pod correctly.

DaemonSets

Desired/current/ready counts and node-level coverage.

Pods

Readiness, status, restarts, node, containers, logs and events.

Deployment │ └── ReplicaSet │ ├── Pod A ─────► Node 1 │ ├── Pod B ─────► Node 2 │ └── Pod C ─────► Node 3 DaemonSet │ ├── Pod D ───────────► Node 1 ├── Pod E ───────────► Node 2 └── Pod F ───────────► Node 3

08 — Product

Relationship-Aware Model

This should become a first-class backend concept rather than a set of frontend filters.

Ingress │ ▼ Service │ selector ▼ Deployment │ owns ▼ ReplicaSet │ owns ▼ Pod │ scheduled on ▼ Node Additional evidence linked to the same object: Pod ──► Containers Pod ──► Events Pod ──► Logs Pod ──► Metrics Pod ──► Last termination reason Pod ──► Volume / PVC relationships

Recommended backend abstraction

Create a graph/relationship package that resolves Kubernetes ownership and placement once, then lets every UI view consume the same normalized relationships.

type RelationshipGraph struct {
    Deployments map[UID]*DeploymentNode
    ReplicaSets map[UID]*ReplicaSetNode
    DaemonSets  map[UID]*DaemonSetNode
    Pods        map[UID]*PodNode
    Nodes       map[string]*NodeNode
}
09 — Product

Logging Architecture

Standard Kubernetes logs and optional file-backed logs should both be handled by the Go backend.

stdout / stderr

Browser │ ▼ GET /api/logs │ ▼ Go │ ▼ Pods(namespace).GetLogs(...) │ ▼ Kubernetes API

File-backed logs

Browser │ ▼ GET /api/file-logs │ ▼ Go │ ▼ Kubernetes exec API │ ▼ tail /configured/path.log
Later improvement: replace 3-second polling for stdout logs with Server-Sent Events or WebSocket streaming backed by the Kubernetes log stream.

12 — Engineering

Backend API Design

The browser should call your local product API, not raw Kubernetes API paths.

EndpointPurpose
GET /api/healthTool health, active context, Kubernetes connectivity, metrics availability
GET /api/contextsAvailable kubeconfig contexts
GET /api/namespacesNamespaces visible to the current user
GET /api/nodesNode health and capacity summary
GET /api/nodes/{name}Node detail, allocated/used/wasted resources and pods
GET /api/workloads?namespace=...Deployments, DaemonSets, ReplicaSets and relationships
GET /api/pods?namespace=...Pod state, ownership, placement and restarts
GET /api/eventsRecent relevant Kubernetes events
GET /api/logsstdout/stderr log retrieval or streaming
GET /api/file-logsOptional configured file-backed log retrieval
GET /api/graphNormalized resource relationship graph
POST /api/actions/restart-podGuarded write action when write mode is enabled
Design rule: keep Kubernetes object-shape quirks inside the Go backend so the frontend works against stable product-level models.
13 — Engineering

Security & RBAC

The safest open-source posture is local-only, RBAC-respecting and read-only by default.

Authentication

  • Use existing kubeconfig authentication
  • Bind the local server to 127.0.0.1 by default
  • Do not copy cluster credentials into browser JavaScript
  • Do not invent a parallel authorization layer

Authorization

  • Kubernetes RBAC remains authoritative
  • Read-only mode is the default
  • Write actions are explicit and gated
  • Surface permission-denied errors clearly
Avoid: shipping a default configuration that allows arbitrary file reads or arbitrary kubectl exec-style commands from the browser.

16 — Publication

How to Position the Paper

The paper should not claim novelty merely because the tool has a Kubernetes GUI.

Weak framing

“We built a Kubernetes dashboard that displays nodes, workloads, logs and events.”

This is too close to existing operational tools and does not establish a research contribution.

Stronger framing

“We built a relationship-aware troubleshooting and capacity-diagnosis system that correlates Kubernetes ownership, placement, resource reservations, runtime usage, events and logs.”

Potential research question

Can automatically correlating Kubernetes workload ownership, pod placement, resource reservations, runtime usage, events and logs reduce the time and cognitive effort required to diagnose operational failures?
17 — Publication

Evaluation Plan

The evaluation is the most important missing piece if the goal is a strong systems or industry paper.

Failure / diagnosis scenarios

  1. CrashLoopBackOff
  2. OOMKilled container
  3. Readiness probe failure
  4. Image pull failure
  5. Unschedulable pod
  6. Node pressure
  7. Uneven pod distribution
  8. Oversized CPU request
  9. Oversized memory request
  10. Deployment replica mismatch
  11. DaemonSet missing on a node
  12. Downstream failure visible primarily in logs/events

Measurements

  • Time to identify root cause
  • Number of commands / interactions
  • Wrong investigative turns
  • Successful diagnosis rate
  • Confidence in diagnosis
  • Capacity waste found
  • Usability / cognitive-effort survey

Comparison design

Same failure scenario │ ├── kubectl workflow ├── terminal/TUI workflow ├── existing Kubernetes GUI workflow └── relationship-aware tool workflow Measure: time + steps + accuracy + wrong turns + confidence
Important: do not invent favorable percentages. The paper becomes stronger only when the observed numbers are collected from reproducible experiments or real engineers.
